## Always-on rules (summary)

- Keep controllers thin; put business logic in `app/Actions/**` / `app/Services/**` (no HTTP objects there).
- Prefer `*Action` for a single business use case or orchestration boundary; prefer `*Service` for reusable domain capabilities shared across flows. If a class is the named entrypoint for one feature, default to an Action.
- Use Form Requests for validation with `toDto()` returning DTOs in `App\Data\**`.
- Form Request `rules()` composes built-in rules, `Illuminate\Validation\Rule`, `App\Support\Validation\**`, and `App\Rules\**`. No multi-line anonymous validation closures with Eloquent or domain logic — extract to `app/Rules/{Domain}/*` or use `Rule::exists()->where(...)`. See `.claude/skills/http-request-validation/SKILL.md` §Validation composition ladder.
- **Reuse before create (DRY)**: before creating any new class (DTO, FormRequest, Action, Service, Resource, component, composable), search the domain directory for an existing artifact with the same shape. Reuse it. Skip single-field wrapper DTOs/Requests — pass the value directly. See `.claude/rules/reuse-before-create.md`.
- Eloquent models MUST define `casts()` for **all** table columns.
- **ALWAYS use `throw_if()` / `throw_unless()` for conditional exception throwing** instead of verbose `if (...) throw ...` blocks. Place guard clauses at the top of methods.
- **ALWAYS use arrow functions (`fn() =>`)** over anonymous functions (`function () {}`). If the body needs multiple lines, extract to a dedicated private method.
- Test-first with Pest when behavior changes; fake external IO (`Http::fake()`, `Storage::fake()`, etc.).
- Quality gates run in this order: Larastan (level 8) → Pint → targeted tests (see `quality-gates` skill).
- Security-sensitive changes (auth, permissions, uploads) should follow the `laravel-security` skill.
- Octane safety: never store request-specific state in statics/singletons.
- Cache discipline: never cache Eloquent models directly; cache raw attributes and hydrate.
- **No redundant trimming**: Laravel's `TrimStrings` middleware already trims all string input before it reaches Form Requests. NEVER add `->trim()` in `toDto()`, Actions, or Services — the value is already trimmed.
- **All API responses MUST use `JsonResource`**: never return raw arrays or bare `response()->json()` from API controllers — even non-model Action results need a dedicated Resource. See constitution §IV and `.claude/skills/http-endpoint-layer/SKILL.md` §Standardized Response Formats.
- **Resources own presentation logic**: value formatting, display-string building, date formatting, computed display flags, label resolution, and display ordering belong in `JsonResource` classes. Resources MAY use presentation-oriented Services (formatters, label resolvers, display builders); they MUST NOT invoke business-logic Actions or domain-mutation Services. Actions/Services return raw domain data — never display-formatted values. See `.claude/skills/http-endpoint-layer/SKILL.md` §Resource boundary.

# Localization Parity

When adding or changing user-facing copy, validation messages, labels, hints, or API error text, update both Russian and English localization sources.

- Backend validation messages must not be hardcoded in Form Requests; use `lang/ru` and `lang/en` keys.
- Frontend UI text must use locale keys in both `resources/js/locales/ru.json` and `resources/js/locales/en.json`.
- If a resource or API type exposes a new user-facing field, update related contract docs and localized validation/help text together.

# Deterministic Test Data

Do not blindly trust factory defaults or Faker output for values under assertion. Primary scenarios MUST use **known, concrete values**.

Canonical samples and merge rules: `specs/079-shared-test-fixtures/` (`constraints.md`, `quickstart.md`, `contracts/test-fixtures.md`). Helpers live under `tests/Support/**` and load via `tests/Pest.php`.

## Prefer concrete values

- Pass explicit attributes / overrides for fields the test asserts or that affect branching (tax number, phone, email, role, dates, status codes).
- Prefer shared sample helpers (`acmeContactAttributes()`, `exampleLlcContactAttributes()`, `adminUser()`, `managerWithCampaign()`, …) over ad-hoc `fake()->...` in the scenario.
- Factories are fine for **wiring** unrelated required relations; they are not a source of truth for asserted fields.

```php
// ❌ BAD — assertion depends on random Faker output
$contact = Contact::factory()->create();
expect($contact->email)->toBe($contact->email); // tautology / flaky coupling

// ✅ GOOD — concrete value, optionally via shared sample
$contact = Contact::factory()->create(acmeContactAttributes([
    'email' => 'lead@example.com',
    'tax_number' => '1234567890',
]));
expect($contact->email)->toBe('lead@example.com');
```

## Generative coverage is secondary

- Property-style / random / large Faker datasets MAY exist as **additional** checks.
- They MUST NOT be the only or primary proof of the behavior under test.
- When uniqueness is required, override explicitly in the scenario instead of hoping Faker stays unique.

## Dates and clocks

- Prefer fixed timestamps (`Carbon::parse('...')`, `Carbon::setTestNow(...)`) over `now()` when the exact instant matters.
- Do not assert against host-local formatting of those values (see `locale-independent-tests` rule).

# Reuse Test Fixtures

Extend the deterministic-data rule: **share one canonical payload, then override only what the scenario needs**.

Canonical families and helpers: `specs/079-shared-test-fixtures/` and `tests/Support/**` (also static fixtures under `tests/Fixtures/**` when file/CSV/JSON shape is shared).

## Prefer shared base + overrides

1. Search `tests/Support/<Domain>/` (and related helpers) before inventing a new attribute array or JSON body.
2. Reuse the sample family that matches the domain (Acme manual lead vs Example LLC / RKO — do not mix default identifiers across families).
3. Customize with `array_replace` / `array_replace_recursive` / helper `$overrides` — change only the fields that matter for this test.

```php
// ❌ BAD — new full JSON body in every test
it('rejects duplicate tax number', function () {
    $payload = [
        'company_name' => 'Acme LLC',
        'phone' => '+7 900 123-45-67',
        'email' => 'lead@example.com',
        // ... 15 more fields copied from the previous test ...
        'tax_number' => '1234567890',
    ];
});

// ✅ GOOD — shared body, local delta
it('rejects duplicate tax number', function () {
    $payload = acmeStoreLeadBody([
        'tax_number' => '1234567890',
    ]);
});
```

```php
// ✅ GOOD — nested AMQP/RKO sample with a small recursive override
$payload = exampleLlcRkoSample([
    'customer' => ['phone' => '+79990001122'],
]);
```

## When to add a new shared helper

- The same attribute/JSON shape appears (or will appear) in **two or more** tests, or is the documented sample for a domain.
- Put it in `tests/Support/<Domain>/` with `$overrides = []` and document canonical defaults in `specs/079-shared-test-fixtures/constraints.md` when the family is cross-cutting.
- Skip a new helper for a one-off shape used in a single test — a local array is fine until reuse appears.

## Do not

- Copy-paste a full payload into each `it()` / `test()` and tweak by eye.
- Invent a second “almost identical” sample family with different default phones/emails for the same domain without an explicit reason.

# Locale-Independent Tests

This product runs in multiple regions and CI environments. Tests MUST NOT depend on the host OS language, locale, or timezone.

Canonical conventions: `specs/081-locale-independent-tests/` (especially `quickstart.md` and `contracts/verification-conventions.md`).

## Do

- Assert **stable codes, field keys, HTTP status, and structure** when behavior is under test — not pasted UI sentences.
- For dates/times in Vitest, assert via shared product formatters (`formatShortDateTime`, `formatDateOnly`, `formatCallbackDisplay` from `@/utils/datetime`) or `t('...')` keys.
- For localized server messages that must be verified, pin locale explicitly and compare with `__()` / `trans()` under each locale (`ru` and `en`), setting locale **before** the request that builds the message.
- Rely on suite baselines (`TZ=UTC` for Vitest; `APP_LOCALE=ru` in `phpunit.xml`; app timezone `UTC` in `config/app.php`) — not on the developer machine language.

## Do not

- Hard-code month names, `dd.mm.yyyy` / `AM`/`PM` strings, or regex-escaped absolute dates in expectations.
- Assume CI uses the same OS locale as a local Mac/Windows/Linux desktop.
- Compare a previously captured response body after a later `app()->setLocale(...)` without re-issuing the request.

```ts
// ❌ BAD
expect(node.text()).toContain('20 июн., 10:00')
expect(node.text()).toContain('Jun 20, 10:00 AM')

// ✅ GOOD
expect(node.text()).toContain(formatShortDateTime('2026-06-20T10:00:00.000Z'))
expect(node.text()).toContain(t('offices.errors.openConflictingOffice'))
```

```php
// ❌ BAD — assumes a single runner locale
expect($response->json('message'))->toBe('Некорректный ИНН');

// ✅ GOOD — bilingual, key-driven
foreach (['ru', 'en'] as $locale) {
    app()->setLocale($locale);
    $response = $this->actingAs($user)->postJson('/api/v1/...', $payload);
    expect($response->json('errors.tax_number.0'))
        ->toBe(__('validation.draft_contacts.tax_number_unique'));
}
```

Fixture names in Cyrillic (`'Иван'`, company names) are fine. Guardrail: `npm run check-locale-independent-tests` (via `make frontend-verify`).

## Frontend conventions (repo-specific)

- Vue 3 SFCs use `<script setup lang="ts">`.
- Only `resources/js/api/**` should define HTTP calls and endpoint URLs, using `resources/js/api/client.ts`.
- Pages, components, composables, and stores may consume typed functions from `resources/js/api/**` when appropriate to their scope.
- Keep page-local state local by default; use composables for reusable client logic and Pinia stores for cross-route or shared state.
- Prefer `@/utils/i18n` for user-facing copy when the surrounding frontend feature already uses translations.
- Keep the current auth approach unless a task explicitly asks to change authentication/token storage.


## Feature tracing defaults

- For backend/API work, start at `routes/api.php`.
- Identify the route URI, middleware, route model bindings, and bound controller before reading deeper files.
- Then trace in this order unless the code clearly shows a different path: `Controller -> Form Request -> DTO -> Action/Service -> Resource -> Model/Policy`.
- Do not start backend feature analysis from arbitrary models, services, or Vue files when a route/controller entrypoint exists.
- For SPA/page behavior, start at `resources/js/router/index.ts` when the behavior is route-driven.
- Then trace in this order: `Route -> Page -> Component/Composable/Store -> resources/js/api/** -> backend route/controller`.
- For non-route shared UI behavior, start from the consuming page or component and follow imports outward.
- Use these tracing paths to build context efficiently, but always prefer the real code entrypoint over the heuristic if they differ.
