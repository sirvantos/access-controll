# Процесс релизов access-controll — рабочая памятка

> Личный конспект для себя (Claude), составлен по итогам изучения истории канала
> Pachca «Центр-инвест» (2026‑05 … 2026‑08) и репозиторных playbook'ов
> (`.claude/commands/smartthings.*`, `.claude/commands/speckit.*`,
> `.claude/skills/release-versioning`, `.specify/memory/constitution.md`).
> Цель: уметь взять релиз из YouTrack и провести его «под ключ» — от ТЗ до
> закрывающей документации — так, как это реально делает команда.

## 1. Источник требований (ТЗ)

- Постановка на релизную серию (например «6.x») готовится продуктом как ТЗ — исторически Google Docs (`docs.google.com/document/...`), иногда с приложенными PDF/DOCX/HTML-макетами.
- ТЗ обсуждается в треде: уточняющие вопросы, правки по комментариям, финальное согласование до начала разработки.
- В YouTrack подготовка ТЗ — это отдельная задача с `Тип задачи = PM/Analytics` или `Spec development`, привязанная к версии релиза (например «Подготовка технического задания и планирование задач для релиза версии 6.х»).
- Технический (speckit) `spec.md` внутри `specs/{NNN}-{slug}/` — это **не то же самое**, что бизнес-ТЗ в Google Docs: спека пишется разработчиком по мотивам ТЗ и тикета, уже в репозитории.

## 2. YouTrack (проект `CI` — «Центр Инвест», `tasker.softezza.ru`)

Кастомные поля задачи:

- **State**: `Open → In Progress → Тестирование → …` (финальные состояния — Done/Closed, не встречались в выборке, но по аналогии).
- **Тип задачи**: `Feature`, `Fix`, `Spec development`, `PM/Analytics`, `DevOps`, `QA`.
- **Релиз** (version bundle) — привязывает задачу к конкретной версии, например `v6.0.0 (загрузка документов РКО)`; также есть `Backlog`.
- **Assignee**, **Исполнитель QA**, **Ревьювер** — три разные роли на задаче.
- Оценочные поля: «Оценка времени», «Оценка разработки», «Оценка тестирования», «Оценка заказчика», «Затраченное время», «Дедлайн», «Критичность», «Priority».
- Метрики качества: «Возврат с ревью», «Возврат с тестирования», «Количество багов», «Bugs» (текст).

Практический вывод: **чтобы «взять релиз из YouTrack»**, нужно отфильтровать задачи по полю `Релиз = v{X.Y.Z}` (или искать `project: CI` + версию в описании) — это даёт полный список: фичи, фиксы, ТЗ-задачи, DevOps-задачи (например «Поднятие rc (stage) контура»), QA-задачи («Тестирование релиза»), задачу на закрывающую документацию.

## 3. Git-flow

- `main` — основная (production-tracking) ветка репозитория.
- `develop` — интеграционная ветка; релизные ветки мержатся обратно в неё после деплоя (`smartthings.release-deploy`, шаг 5).
- `feature/CI-XXX` — одна ветка на тикет/спеку; спека внутри репозитория ссылается на неё строкой `**Feature Branch**: feature/CI-XXX` (см. `specs/088-compliance-collection-initiator/spec.md`). Через GitLab MR (`gitlab.softezza.ru/.../merge_requests/...`), ревью коллегой перед мержем (иногда явно «не мержить, напиши в коменты»); при высокой связанности задач допускается одна ветка/MR на несколько тикетов, если разводить их дороже, чем совместно ревьюить.
- `release/v{X.Y.Z}` — релизная ветка; версия `{tag}` берётся из имени ветки.
- Коммиты: `<type>: <краткое описание>` в повелительном наклонении, ≤72 символа в первой строке; **никогда не коммитить без явного подтверждения пользователя** (`.claude/skills/git/SKILL.md`).

## 4. Spec-Driven Development (от тикета до кода)

Канонический путь одной фичи/тикета:

1. `/speckit-specify` — создать `specs/{NNN}-{slug}/spec.md` (номер спеки — сквозной, **не совпадает** с номером тикета CI-XXX). Каталог спеки пишется в `.specify/feature.json` и не обязан совпадать с именем git-ветки.
2. `/speckit-clarify` — снять неоднозначности (до 5 вопросов), закодировать ответы в спеку.
3. `/speckit-plan`, `/speckit-tasks` — план и разбивка на задачи.
4. Реализация: следуя `.specify/memory/constitution.md` (архитектурные non-negotiable) и релевантным `.claude/skills/*` (операционные playbook'и по слоям — `action-layer`, `http-endpoint-layer`, `http-request-validation`, `model-orm-layer`, `laravel-security`, и т.д.). Делегирование в subagents `backend`/`frontend`/`contract` — **только вручную**, по явному запросу пользователя (`.claude/rules/manual-subagents.md`), координация через handoff-пакет из `.claude/skills/subagent-orchestration/SKILL.md`.
5. `/speckit-converge` — сверить код со spec/plan/tasks и дописать оставшуюся работу в `tasks.md`, затем снова `/speckit-implement`, пока отчёт не станет Converged.
6. `/speckit-analyze` при необходимости — сверка согласованности артефактов spec/plan/tasks.
7. Quality gates (см. §6) → MR в GitLab → ревью коллегой → мерж (в `develop` или в интеграционную ветку релиза).
8. `/smartthings.unreleased` — создать фрагмент `releases/unreleased/{branch}.md`, если ветка вносит deployment-значимые изменения (миграции, .env, breaking changes).

## 5. Quality gates (обязательный порядок)

```
vendor/bin/phpstan analyse -c phpstan.neon --no-progress --memory-limit=1G   # Larastan level 8
vendor/bin/pint --dirty                                                      # форматирование
php artisan test --compact <path|--filter>                                   # целевые Pest-тесты
```

Frontend-only изменения: `npm run test:run`, `npx vue-tsc --noEmit` (+ `npm run build`, если задет tooling/bootstrap). Прогонять `make quality-gates` **только** если менялся код/тесты/фронтенд/CI-конфиг — не для документации (`.claude/rules/quality-gates-scope.md`).

## 6. Релизный цикл (три отдельные команды, не взаимозаменяемые)

| Шаг | Команда | Что делает |
|---|---|---|
| 1 | `/smartthings.release-prepare <spec-ids или CI-ids>` | На чистой `release/v{X.Y.Z}`: собирает `releases/{tag}.md` из спек + фрагментов по шаблону `releases/TEMPLATE.md`, гоняет quality gates, коммитит release notes (после подтверждения) |
| 2 | `/smartthings.release-deploy` | Quality gates ещё раз → версия в `composer.json` (канонический источник версии, читается в рантайме/UI-футере) → аннотированный тег `v{tag}` → `scripts/build_deploy_zip.sh` (нужен `BACKUP_PASSWORD`) → мерж `release/v{tag}` обратно в `develop`. Каждый шаг — с явным подтверждением пользователя |
| 3 (в конце серии, напр. 5.x) | вручную по living docs | В Spec Kit 1.0.12 нет `/speckit-finalize-release-docs`. Закрывающие документы правятся в `docs/**` и `releases/` напрямую |

Реальный цикл dev→test, наблюдаемый в Pachca: деплой на dev → анонс в чате → QA тестирует → «успешно прошёл тестирование» → иногда отдельный stage/RC-контур для ЦИ (`ci-rc.softezza.ru`) перед сдачей → у самого ЦИ есть свой тестовый стенд (`showroom21.dev.cinet.ru`, `ci-dev.softezza.ru`) и продовая обратная связь через их Mattermost. Хотфиксы (например 4.0.1) заводятся отдельным релизом поверх уже протестированного, если параллельно готовится следующий крупный релиз (5.x/6.x) — вплоть до временного отката dev-стенда на хотфиксовую версию, чтобы корректно её проверить в изоляции.

## 7. Закрывающая документация — КЛЮЧЕВОЙ СДВИГ на 5.1.0

- По договору с ЦИ команда **обязана** предоставлять закрывающую документацию на каждый релиз (сообщение Владимира Алтухова, 10.08.2026).
- **До 5.1.0** (включая 4.0.0, 4.0.1, и раньше — например 2.4.2): закрывающая документация — это **отдельный Google Doc**, который пишется вручную после релиза и рассылается ссылкой в Pachca («Делаю первый раз, весь документ сам просмотрел, но перепроверьте лучше кто-нибудь»). Документация в репозитории при этом тоже поддерживалась в актуальном состоянии параллельно, но именно Google Doc был тем, что уходило клиенту.
- **Перелом**: 07.08.2026, тред по релизу 4.0.1, Максим Будьков — **«документация теперь есть в релизе»** (т.е. в самом репозитории, без отдельного Google Doc). Сразу следом Степан Бондарь описывает требование к полному комплекту: «свежая схема бд, свежие релиз ноты, свежие инструкции, деплоймент документ» + проверка на уязвимости `npm`/`composer`. В Spec Kit 1.0.12 отдельной команды для этого пакета нет.
- **С 5.1.0 и далее**: единственный источник истины — репозиторий:
  - `releases/{version}.md` — по каждому релизу, из `releases/TEMPLATE.md`.
  - `releases/release-notes.md` — сводный чейнджлог по всем версиям/линейкам.
  - Living docs `docs/`: `RELEASE_NOTES.md`, `DEPLOYMENT_server.md`, `DEPLOYMENT_docker_multi_stand.md`, `db/DATABASE_SCHEMA.md` (+ `db_schema.mermaid/svg/uml`), `USER_MANUAL_{ADMINISTRATOR,DIRECTOR,MANAGER}.md`.
  - Клиентский пакет (8 документов, **только русская проза**, генерируется из living docs, никогда не пишется в обход них) в `temp/release-docs/{MAJOR}.x/` — **не коммитится, в .gitignore**: «Примечания к выпуску», «Инструкция», по «Инструкция» на каждую роль (Администратор/Директор/Менеджер), «Схема базы данных», «Архитектура БД», «Отчет автотесты» (с реальным выводом `make larastan`, `pint --test`, `php artisan test`, `composer audit`, `npm audit`).
  - Локализационная дисциплина: клиентский пакет проверяется на англицизмы; вхождения в код/командах допустимы, в прозе — нет. Шаблоны `.specify/templates/release-docs/` в Spec Kit 1.0.12 не входят.
  - Больше нет отдельной Google Doc-стадии: то, что раньше уходило клиенту ссылкой на Google Doc, теперь **является файлами репозитория** (плюс временный сгенерированный пакет для ручной фильтрации/передачи).

## 8. Чеклист «взять релиз из YouTrack и довести под ключ»

1. В YouTrack найти все задачи с `Релиз = v{X.Y.Z}` (project `CI`) — фичи, фиксы, DevOps/QA-задачи, задачу на ТЗ, задачу на закрывающую документацию.
2. Для задач без спеки — `/speckit-specify` (ветка `feature/CI-XXX`) → `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` → реализация по constitution + skills → `/speckit-implement` → `/speckit-converge` → quality gates → MR → мерж.
3. По ходу — `/smartthings.unreleased` на каждую deployment-значимую ветку.
4. Ветка `release/v{X.Y.Z}` от `develop` → `/smartthings.release-prepare <ids>` → `/smartthings.release-deploy`.
5. Статусные сообщения по вехам (деплой на dev / протестировано / стейдж) — по аналогии с тоном канала «Центр-инвест», но отправка сообщений пользователю требует явного подтверждения (правило про explicit permission для отправки сообщений).
6. В конце серии — сверка living docs и клиентского пакета вручную, проверка локализации, финальный отчёт с таблицей документов и списком того, что требует ручных действий (скриншоты, coverage, E2E-матрица).
7. Никакого отдельного Google Doc — весь deliverable для ЦИ теперь строится из репозитория.
